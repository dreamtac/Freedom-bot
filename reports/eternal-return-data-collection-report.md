# 이터널 리턴 전적 수집·DB 설계 보고서

작성일: 2026-09-15 · 검증 닉네임: **홉빵맨**

## 1. 결론

- 기존 SQLite에 유저별 경기 기록과 수집 진행 상태를 저장한다.
- 등록 유저는 5분마다 갱신하고, `/전적` 직접 검색은 다음 자동 주기를 기다리지 않고 우선 갱신한다.
- 기본·상세 전적에 필요한 데이터는 **사용자 경기 목록 응답에 함께 포함**된다. 경기별 상세 API를 매번 호출할 필요가 없다.
- 사용자 ID를 재사용하면 최신 상태 확인은 보통 **유저당 API 1회**다. 처음 100경기를 모으려면 **11회**, 500경기는 **51회**가 필요하다.
- 이름·시즌 등 공통 데이터는 제안 구성 기준 초기 **API 8회 + 언어 파일 다운로드 1회**다. 유저마다 반복하지 않는다.
- 모든 이터널 리턴 API 호출과 재시도는 하나의 대기열에서 요청 시작 간격을 최소 1.1초로 제어한다.

이 문서는 합의한 기능 범위와 구현 시 확인할 사항을 정리한 최종 보고서다. 2026-09-16 기준 0단계 개발·운영 분리, 1단계 공통 API 요청 제어, 2단계 DB와 데이터 모델, 3단계 최신·과거 전적 수집을 완료했다. 5분 자동 갱신·시즌 분석·새 화면은 아직 구현 전이며 운영 DB는 변경하지 않았다.

**최종 범위:** `/전적`, `/상세전적`, `/시즌전적`, `/전적분석`을 제공한다. 시즌전적에는 검색한 유저 자신의 실험체별 평균 피해량만 표시한다. 전체 유저·친구·외부 표본과의 비교, 이를 위한 참가자 수집, 루트 제목·구성 상세는 제외한다. 본인의 과거와 최근 비교는 유지한다. 앞 절의 확장 API·루트 상세 설명은 조사 이력이며 구현 대상은 12절을 기준으로 한다.

### 사실과 가정의 구분

| 항목 | 기준 |
|---|---|
| 개인키 초당 1회 | 사용자가 알려준 해당 키의 제한을 설계 전제로 사용 |
| 경기 페이지당 10개 | 홉빵맨의 첫째·둘째 페이지에서 각각 10개, 중복 0개 확인 |
| 다음 페이지 | 응답의 `next`를 `?next=값`으로 전달해 추가 10경기 조회 확인 |
| 페이지 규격의 보장 범위 | 제공된 레퍼런스에는 페이지 크기·`next`가 명시되지 않음. 아래 계산은 현재 관측한 동작 기준 |
| 자동 확인 간격 | 현재 로컬 `NEWS_POLL_INTERVAL_MS=300000`, 즉 5분 |
| 호출 수 표 | 정상 응답, 재시도 없음, UID 재사용 가능 여부를 표에 명시 |
| 시간 표 | API 1회당 약 1.1초의 처리 예산. 응답 지연·재시도·우선 요청의 대기는 별도 |

공식 문서는 최근 90일의 경기 조회를 설명하며 닉네임 변경 전 경기는 제외한다고 명시한다. UID도 닉네임 변경 시 달라지므로 영구 계정 ID로 취급하지 않는다. 이번 검증으로 전체 90일 기록이나 모든 모드의 필드 제공을 확인한 것은 아니다. [공식 레퍼런스](https://developer.eternalreturn.io/static/media/OpenAPI_KR_20260724.html)

## 3. DB에 저장할 데이터

### A. 유저 및 자동 수집 대상: `er_players`

| 저장 항목 | 용도 |
|---|---|
| 내부 유저 ID | DB에서 사용하는 자체 식별자 |
| 조회 닉네임, API UID | 해당 닉네임으로 API 조회. UID 변경을 감지하면 자동으로 과거 유저와 합치지 않음 |
| UID 확인 시각 | 캐시 재확인 시점 관리 |
| 자동 수집 여부 | 수동 검색한 모든 사람을 자동 등록하지 않고 지정한 친구만 주기 조회 |
| 등록 시각 | 수집 대상 관리 |

닉네임 변경은 추적 대상을 새 닉네임으로 갱신하는 절차가 필요하다. 변경 전후 기록의 연결은 별도 확인 없이 추정하지 않는다.

### B. 경기 기록: `er_player_games`

**한 행은 한 유저의 한 경기**다. 유저 식별자와 `gameId` 조합을 고유하게 두어 친구들이 같은 경기에 참가해도 서로의 기록을 따로 저장한다.

| 기능 | DB에 보관할 값 | API 필드 |
|---|---|---|
| 식별 | 경기 ID, 경기 당시 닉네임 | `gameId`, `nickname` |
| 시각 | 시작 시각, 플레이 시간 | `startDtm`, `playTime` |
| 실험체 | 실험체 코드 | `characterNum` |
| K/D/A | 킬·데스·어시스트 각각 | `playerKill`, `playerDeaths`, `playerAssistant` |
| 팀킬 | 해당 응답의 팀 전체 킬 수 | `teamKill` |
| 순위 | 경기 순위 | `gameRank` |
| 가한 피해 | 플레이어 대상 피해 | `damageToPlayer` |
| 받은 피해 | 플레이어에게 받은 피해 | `damageFromPlayer` |
| 야생동물 피해 | 몬스터에게 가한 피해 | `damageToMonster` |
| 추가 보관 | 몬스터에게 받은 피해 | `damageFromMonster` |
| 루트 | 시작 시 선택한 루트 번호 | `routeIdOfStart` |
| 특성 | 핵심 특성과 보조 특성 코드 목록 | `traitFirstCore`, `traitFirstSub`, `traitSecondSub` |
| 장비 | 슬롯별 장비 코드 | `equipment` |
| 지역 | 시작·사망 지역 원본 값 | `placeOfStart`, `placeOfDeath` |
| 비교 조건 | 시즌·매칭 모드·팀 모드 | `seasonId`, `matchingMode`, `matchingTeamMode` |
| 패치 구분 | 응답에 존재하는 버전 값 | `versionSeason`, `versionMajor`, `versionMinor` |
| 수집 관리 | 최초 저장·마지막 갱신 시각 | 봇이 생성 |

이번 첫 페이지 10경기에서 위 주요 경기 필드는 확인됐지만 `versionSeason`은 모두 누락됐다. 없는 필드는 `NULL`로 저장하며, 피해량·데스 등의 누락을 0으로 바꾸지 않는다. 평균은 값이 있는 경기만 대상으로 계산하고 항목별 유효 경기 수를 표시한다.

장비·특성은 JSON 형태로 저장해도 된다. 평균 집계에 쓰는 수치·시간·실험체·시즌은 독립된 열로 저장한다. 조회를 빠르게 하기 위해 유저+시각, 유저+모드+실험체+시각 기준의 인덱스를 고려한다. 초기에는 필요한 필드만 보관하고 경기 응답 전체 JSON의 영구 보관은 필수로 하지 않는다.

#### 표시 의미의 주의점

- `damageToMonster`는 피해량이며 야생동물 처치 수와 다르다.
- 받은 피해는 기본적으로 `damageFromPlayer`를 표시한다. 몬스터 피해까지 합산하려면 UI에서 그 의미를 명확히 한다.
- 공식 정의에서 `teamKill`은 플레이어 기준 경기 종료 시점의 팀킬이다. 항상 팀 전체 경기의 최종 종료 값이라고 확대 해석하지 않는다.
- `placeOfDeath`는 공식 문서에서 레거시 필드로 분류되며 해석 지원 제한이 있다. 값을 보관하되 누락·변환 실패 시 ‘확인 불가’로 표시한다.
- 패치 값이 일부 누락되면 완전한 패치 번호를 임의로 만들지 않는다.

### C. 수집 진행 상태: `er_sync_state`

| 저장 항목 | 필요한 이유 |
|---|---|
| 마지막 시도 시각, 성공 시각 | 실패를 ‘최신 상태’로 오인하지 않기 |
| 최신 구간 수집 완료 경계 | 새 기록을 어디까지 빠짐없이 수집했는지 판단 |
| 가장 오래된 수집 시각 | 분석 가능한 과거 범위 표시 |
| 과거 수집용 `next` | 중단·재시작 후 이어서 수집 |
| 초기 목표와 완료 여부 | 예: 100경기 수집 완료/진행 중 |
| 다음 재시도 시각, 오류 상태 | 제한·일시 오류 이후 재개 |

최신 갱신 경계와 과거 수집 커서는 분리한다. 새 경기를 일부 저장한 뒤 실패해도 전체 구간을 수집한 것처럼 완료 경계를 옮기지 않는다. 저장 자체는 중복에 안전하게 수행하고, 재시작 시 미완료 구간을 다시 확인한다.

### D. 공통 이름 데이터: `er_reference_cache`

실험체·특성·장비·지역의 코드와 이름, 시즌 자료, 한글 번역, 테이블 해시와 갱신 시각을 저장한다. 모든 유저가 공유하며 봇 재시작 후에도 DB에서 재사용한다.

평균 피해량·순위·K/D/A·팀킬은 초기에는 별도 영구 테이블 없이 경기 기록에서 계산한다. 이미 수집된 구간을 분석하는 추가 API 호출은 **0회**다. 실험체별로도 같은 방식으로 집계한다.

## 4. 사용할 엔드포인트와 횟수

기본 주소: `https://open-api.bser.io`

| 용도 | 엔드포인트 | 호출 횟수와 시점 |
|---|---|---|
| 닉네임 → UID | `GET /v1/user/nickname?query={nickname}` | 최초 등록 1회. 이후 캐시 재확인 또는 UID 문제 시 추가 |
| 최신·과거 경기 | `GET /v1/user/games/uid/{uid}` | 페이지당 1회. 이후 페이지에는 실측으로 확인한 `?next={next}` 사용 |
| 전체 참가자 상세 | `GET /v1/games/{gameId}` | 제안한 기본·상세 전적 수집에는 0회 |
| 시즌 통계 | `GET /v2/user/stats/uid/{userId}/{seasonId}/{matchingMode}` | 요청한 기간·경기 수별 비교는 DB에서 계산하므로 0회 |
| 현재 랭크 | `GET /v1/rank/uid/{userId}/{seasonId}/3` | 분석 수집에는 0회. 별도 랭크 명령 사용 시 UID 확인 외 1회 |
| 루트 구성 상세 | `GET /v1/weaponRoutes/recommend/{routeId}` | 루트 번호만 표시하면 0회. 구성까지 필요하면 캐시에 없는 루트당 1회 시도 |
| 테이블 목록·변경 확인 | `GET /v2/data/hash` | 공통 자료 초기화 및 정기 점검 때 1회 |
| 이름·시즌 원본 | `GET /v2/data/{metaType}` | 아래 6개 테이블을 각각 1회 |
| 한글 번역 URL | `GET /v1/l10n/Korean` | 한글 자료 초기화·정기 갱신 때 1회 |

사용자 경기 목록과 매치별 조회는 모두 BattleUserResult를 제공한다. 이번 실제 경기 목록에서도 상세 화면에 필요한 장비·특성·지역·루트 번호를 확인했다. 따라서 ‘상세 전적’을 누를 때마다 매치별 API를 호출할 이유는 없다.

루트 API는 추천 루트 조회 엔드포인트다. 임의의 과거 루트가 항상 조회되거나 경기 당시 구성 그대로 복원된다고 보장하지 않는다. 초기 범위는 **사용한 루트 번호 표시**를 기준으로 잡는다. [공식 엔드포인트 설명](https://developer.eternalreturn.io/static/media/OpenAPI_KR_20260724.html)

### 공통 자료의 정확한 초기 비용

| 자료 | API 호출 |
|---|---:|
| `hash` | 1 |
| `Character`, `Area`, `Trait` | 3 |
| `ItemWeapon`, `ItemArmor` | 2 |
| `Season` | 1 |
| `l10n/Korean` | 1 |
| **합계** | **8** |

별도로 `l10Path` 응답 URL에서 한글 파일을 다운로드하는 HTTP 요청 **1회**가 필요하다. 이는 Open API 엔드포인트 호출과 구분하며, 같은 제한이 적용되는지는 제공 레퍼런스에서 확인되지 않았다. API 키를 다운로드 URL로 전달하지 않는다.

위 6개 데이터 테이블은 이번 `/v2/data/hash` 응답에 존재하는 것을 확인했다. 캐릭터·장비별 개별 조회가 아니라 테이블 전체를 한 번 가져와 공유한다. 예상 밖 장비 코드가 발견되면 필요한 테이블을 추가한다.

정기 갱신은 예를 들어 하루 1회: 해시 1회 + 변경된 테이블 k회 + 한글 URL 1회 + 파일 다운로드 1회. 즉 **API 2+k회, 별도 HTTP 1회**다. 로컬에 없는 코드가 나타나면 조기 갱신한다. 이 주기는 제안이며 5분마다 반복할 필요는 없다.

현재 코드는 공통 자료에 API 9회와 언어 다운로드 1회를 사용하고 메모리에 6시간 캐시한다. 위 설계는 현재의 소비품·기타·특수 아이템 테이블을 기본 수집에서 빼고, 시즌·해시를 추가한 제안이다.

## 5. 상황별 호출량과 시간

### A. 처음 유저를 등록할 때

전제: 공통 자료가 준비돼 있고, 목표만큼 조회 가능한 경기가 있으며 모드 필터 없이 N경기를 수집한다.

**호출 수 = 닉네임 조회 1회 + 경기 목록 `ceil(N / 10)`회**

| 목표 | 닉네임 | 경기 목록 | API 합계 | 1.1초/회 처리 예산 |
|---|---:|---:|---:|---:|
| 최신 10경기 | 1 | 1 | 2 | 약 2.2초 |
| 100경기 | 1 | 10 | 11 | 약 12.1초 |
| 500경기 | 1 | 50 | 51 | 약 56.1초 |
| 1,000경기 | 1 | 100 | 101 | 약 111.1초 |
| 친구 10명 × 100경기 | 10 | 100 | 110 | 약 2분 1초 |
| 친구 10명 × 500경기 | 10 | 500 | 510 | 약 9분 21초 |

DB도 공통 자료도 처음이라면 위 합계에 **API 8회 + 파일 다운로드 1회**를 한 번만 더한다. 예: 한 명의 100경기는 API 총 19회, 다운로드 포함 총 HTTP 20회다.

시간은 응답 지연을 포함한 실측치가 아니다. 빈 대기열에서 C회 요청의 시작 간격만 계산하면 `(C-1)×1.1초`이며, 위 표는 편의상 `C×1.1초`의 예산을 잡았다. 네트워크와 실제 스케줄링에 따라 달라진다.

랭크 100경기를 목표로 할 때 일반 경기가 섞여 있으면 더 많은 페이지가 필요하다. 기록이 부족하면 종료 응답까지 확인하고 실제 표본 수를 표시한다. 90일 전체 수집은 닉네임 조회 1회 + 실제 페이지 수 P회이며, 끝 확인 방식에 따라 빈 페이지 호출이 추가될 수 있다.

### B. 이미 저장한 유저를 갱신할 때

전제: UID를 재사용하고 저장된 최신 완료 지점을 찾을 때까지 페이지를 읽는다.

| 저장 후 새 경기 수 | 경기 목록 호출 예산 | 이유 |
|---|---:|---|
| 0 | 1 | 최신 페이지를 확인해야 변화 없음을 알 수 있음 |
| 1~9 | 1 | 첫 페이지에 새 경기와 기존 저장 경기가 함께 있음 |
| 10~19 | 2 | 다음 페이지에서 기존 완료 지점 확인 |
| 20~29 | 3 | 동일 방식으로 연결 지점까지 확인 |

보수적으로 기존 완료 지점과 겹치는 페이지까지 읽으면, 새 경기 G개에 대해 `floor(G/10)+1`회다. 응답 종료나 검증된 경계 정보로 더 일찍 끝낼 수 있는 경우는 줄어든다. 기존 경계가 90일 범위 밖으로 나갔다면 이 공식으로 수집 완전성을 보장할 수 없으며 기록 공백을 표시해야 한다.

UID 재확인이 필요하면 위 수에 닉네임 조회 1회가 추가된다. 이미 읽은 페이지의 기록은 중복 없이 갱신해 서버가 수정한 최신 수치도 반영한다.

### C. 친구 10명을 5분마다 확인할 때

UID 캐시가 유효하고 새 경기가 없거나 각자 9경기 이하인 평상시 기준:

- 한 주기: **10회**, 처리 예산 약 11초.
- 24시간 계속 실행하면 하루 288주기: **2,880회/일**.
- 매번 UID를 재조회하면 한 주기 20회, 하루 **5,760회**.
- 추가 페이지·수동 검색·공통 자료 갱신·재시도는 별도다.

초당 1회라는 사용자 제공 제한에 맞춘 계산이며, 일일 호출 할당량이 없다는 뜻은 아니다. 초당 상한을 모두 채우지 않고 수동 요청을 위한 여유를 둔다.

### D. `/전적`, 상세 화면, 분석 요청

| 요청 | 필요한 추가 호출 |
|---|---|
| 기존 유저 `/전적` 검색 | 보통 경기 목록 1회, 새 기록이 많거나 UID 재확인이 필요하면 증가 |
| 신규 유저 `/전적` 검색 | UID 1회 + 최신 페이지 1회로 우선 표시 |
| 저장된 경기의 상세 화면 | 공통 자료가 있으면 0회 |
| 저장된 구간의 전적 분석 | 0회 |
| 최신 갱신을 포함한 분석 | 평상시 경기 목록 1회 + DB 집계 |
| 부족한 과거 표본 확보 | 필요한 추가 페이지당 1회 |

## 6. 실행 원칙

1. 엔드필드와 동일한 5분 설정으로 전적 갱신을 시작하되 서로의 완료·성공 여부에 종속시키지 않는다.
2. 수동 검색, 자동 갱신, 공통 자료, 재시도를 모두 같은 API 대기열에 넣는다. 현재 코드의 개별 250ms 대기는 초당 1회 제어를 대신할 수 없다.
3. 수동 검색을 우선하고 최신 자동 갱신, 과거 대량 수집 순서로 처리한다. 과거 수집은 유저별 몇 페이지씩 번갈아 처리해 특정 유저가 계속 밀리지 않도록 한다.
4. 같은 유저의 진행 중 갱신은 공유한다. 다음 5분 주기가 와도 중복 작업을 쌓지 않는다.
5. 페이지별 저장과 완료 지점 갱신을 일관되게 처리한다. 미완료 수집은 다음 실행에서 재개한다.
6. 제한 응답을 받으면 대기열 전체에 휴지 시간을 적용하고 재시도도 요청 간격 제한을 따른다. 인증 오류와 호출 제한을 가능한 응답 근거로 구분한다.
7. 검색 결과에는 마지막 성공 갱신 시각, 분석에는 사용 구간·표본 수·수집 완료 여부를 표시한다. 실패한 갱신을 최신 결과로 표시하지 않는다.
8. 평균은 같은 모드·실험체 등 정한 조건으로 비교한다. 누락 값은 제외하며 표본이 적거나 구간이 덜 수집됐으면 이를 표시한다.

## 8. 추가 검토: 게임 모드와 확장 데이터 후보

검토·추가 실측: 2026-09-15 21:40 KST. 홉빵맨의 닉네임 조회와 최신 경기 목록을 총 2회 호출했다. 아래 추가 필드는 확인한 랭크 10경기에 모두 존재했다. 다른 유저·시즌·모드에서도 항상 제공된다는 의미는 아니므로 선택 필드로 저장한다.

### 8.1. 일반·랭크 구분은 필수 저장

`matchingMode`와 `matchingTeamMode`는 이미 3절의 필수 저장 항목이다. 공식 모드 표는 다음과 같다.

| `matchingMode` | 표시 |
|---|---|
| 2 | 스쿼드 일반 |
| 3 | 스쿼드 랭크 |
| 6 | 코발트 일반 |
| 9 | 론울프 |

일반·랭크만 저장하는 참/거짓 값 대신 **원본 숫자 코드**를 저장한다. 새 모드나 알 수 없는 코드를 일반으로 처리하지 않는다. 기본 분석은 일반과 랭크를 분리하고 코발트·론울프는 별도 조건으로 다룬다. `matchingTeamMode`도 최신 공식 정의에서 1=론울프, 3=스쿼드, 4=코발트다. 현재 코드의 Solo/Duo 명칭은 향후 구현 때 이 정의에 맞춰 정리할 필요가 있다. [공식 모드 표](https://developer.eternalreturn.io/static/media/OpenAPI_KR_20260724.html)

### 8.2. 우선 추가 보관 권장 — 경기 수집 API 추가 0회

공식 문서에서 MMR 전후 값은 일부 접근자에게만 제공될 수 있다고 설명한다. 이번 개인키 응답에는 두 값이 있었지만 필수값으로 요구하지 않는다. `escapeState`의 실측 값에는 0도 있었으므로 문서에 설명된 1~3 이외 값을 임의로 탈출 실패로 바꾸지 않는다. [공식 필드 정의](https://developer.eternalreturn.io/static/media/OpenAPI_KR_20260724.html)

친구 조합은 **같은 `gameId`와 같은 `teamNumber`**인 저장 기록을 연결해 구한다. `preMade`나 매칭 유형만으로 함께한 사람의 이름을 알아낼 수는 없다. 지원 수치의 높은 평균을 곧바로 실력 향상이나 승리 원인으로 단정하지 않는다.

같은 응답에서 더 많은 필드를 저장하므로 **100경기 최초 수집 11회, 500경기 51회라는 기존 호출 수는 그대로**다. 다만 이름 해석에 새 데이터 테이블이 필요하면 공통 자료 초기 호출은 테이블당 1회 늘어날 수 있다. 코드 수집과 이름·이미지 표현 비용은 구분한다.

### 8.4. 저장된 데이터로 만들 수 있는 지표 — API 0회

- 모드별 우승률·상위 3위 비율·연속 우승과 평균 순위.
- 분당 피해량과 분당 사냥 수: `playTime > 0`이고 필요한 값이 있는 경기만 계산한다. 평균 경기별 비율과 전체 합계의 비율 중 계산 방식을 명시한다.
- 실험체·무기·전술 스킬·루트별 성적 비교. 표본 수와 모드·시즌을 함께 표시한다.
- 기간별 RP 증감 합계. 중간 기록이 빠지면 전체 기간의 완전한 변화로 표시하지 않는다.

`(킬+어시스트)/팀킬`을 킬 관여율로 쓰는 기능은 현재 팀킬 필드의 기준 시점·처치 집계 방식과 분모 0 처리까지 검증한 뒤 도입한다.

### 8.5. 추가 API 후보 — 기능을 사용할 때만 호출

아래 비용은 UID가 준비된 상태의 정상 요청 기준이다. 이번 추가 검증에서는 이 엔드포인트들을 실제 호출하지 않았으며 공식 레퍼런스에 근거해 후보로 검토했다.

| 기능 후보 | 엔드포인트 | 추가 호출 | 권장 방식 |
|---|---|---:|---|
| 같은 경기 전체 참가자 비교 | `GET /v1/games/{gameId}` | 캐시에 없는 경기당 1회 | 사용자가 그 경기의 전체 참가자를 요청할 때 조회 |
| 시즌 성적표 | `GET /v2/user/stats/uid/{userId}/{seasonId}/{matchingMode}` | 시즌·모드 조합당 1회 | 별도 시즌 요약 요청 때 사용. 최근 N경기 분석의 대체재는 아님 |
| 현재 점수·랭킹 | `GET /v1/rank/uid/{userId}/{seasonId}/3` | 유저·시즌당 1회 | 랭크 명령이나 낮은 빈도의 스냅샷 저장 |
| 루트 제목·구성 | `GET /v1/weaponRoutes/recommend/{routeId}` | 캐시에 없는 루트당 1회 시도 | 상세 요청 때 조회. 과거 경기 당시 구성 복원은 보장되지 않음 |

| 통합·서버 상위 랭커 | `GET /v1/rank/top/{seasonId}/3` 또는 뒤에 `/{serverCode}` | 목록당 1회 | 랭킹 구경용. 같은 실험체 평균 피해량을 바로 제공하는 API는 아님 |

공식 엔드포인트 용도는 [API 레퍼런스](https://developer.eternalreturn.io/static/media/OpenAPI_KR_20260724.html)를 기준으로 했다. 전체 참가자를 매번 수집하면 100경기 초기 비용이 11회에서 최대 111회로 늘어난다. 다른 친구와 공유하는 경기 ID는 한 번만 조회해 재사용할 수 있다. 현재 요청한 개인 전적·분석에는 이 추가 수집이 필요하지 않다.

### 8.6. 최종 추천

**필수 데이터 + 8.2절의 추가 후보를 선택 필드로 저장**하는 것을 추천한다. 8.3절은 선택 후보로 남긴다. 최종 구현에서는 본인 기록을 중심으로 회복·시야·사냥·전술 스킬 등 향후 활용에 필요한 데이터를 보관하고, 다른 유저와의 비교 기능은 추가하지 않는다. 별도 API 중 이번에 사용할 것은 10절의 시즌 프로필 조회다.

이 항목을 조사할 당시에는 보고서에만 반영했다. 이후 2단계에서 선택 필드를 저장 모델에 추가했으며 운영 DB에는 적용하지 않았다.


## 9. 루트 개별 조회 실측 정정

2026-09-15, 홉빵맨 최신 경기 65306335의 루트 5212를 실제 조회했다.

- 최신 HTML 레퍼런스를 바탕으로 시도한 `/v1/weaponRoutes/recommend?routeId=5212`는 HTTP 200이지만 다른 추천 루트 100개를 반환했으며 5212는 없었다.
- [공식 이전 레퍼런스](https://developer.eternalreturn.io/static/media/Docs_KR_20250710.pdf)에 명시된 `/v1/weaponRoutes/recommend/5212`는 HTTP 200으로 해당 루트 하나를 반환했다.
- 따라서 개별 루트는 **경로에 ID를 붙이는 방식**을 사용한다. 위 엔드포인트 표도 실측 결과로 수정했다.
- 단일 조회의 `result`는 배열이 아닌 객체였으며, 키는 `recommendWeaponRoute`, `recommendWeaponRouteDesc`였다.
- 루트 제목은 **호묘부활**, 제작자 닉네임은 **인세인**, 루트 버전은 16, 게임 버전은 12.2.0이었다.
- 목표 장비·후반 장비·특성·전술 스킬·지역 순서·스킬 순서·설명까지 반환됐다. 이 값은 현재 저장된 루트 정보이며 해당 경기 시점의 변경 이력을 복원한 것은 아니다.
- 원문 응답: `hoppangman-route-5212-raw.json`. 보기 좋게 들여쓰기한 동일 데이터: `hoppangman-route-5212.json`.
- 이번 확인은 닉네임 1회 + 최신 경기 1회 + 쿼리 방식 검증 1회 + 경로 방식 조회 1회로 총 4회였다. 정상적인 동일 기능의 호출 예산은 UID가 없을 때 3회, 준비돼 있으면 2회다.

## 10. 시즌전적 화면과 명령어 역할

### 10.1. 화면 분리

| 명령어 | 역할 |
|---|---|
| `/전적` | 최근 경기 목록. 상단에 현재 티어를 짧게 표시하고 [시즌전적 보기] 버튼 제공 |
| `/상세전적` | 선택한 경기의 장비·특성·지역 등 상세 정보. 루트는 번호만 표시 |
| `/시즌전적` | 현재 시즌 티어·RP, 선호 실험체 TOP 5, 실험체별 경기 수와 평균 플레이어 피해량 |
| `/전적분석` | 과거와 최근의 성적 변화 비교 |

`/시즌전적`의 기본 대상은 현재 시즌 스쿼드 랭크다. 선호 실험체는 승률이나 피해량이 아니라 **시즌 랭크 플레이 횟수 내림차순**으로 정렬한다. 5개 미만이면 실제 플레이한 실험체만 표시한다. 동률은 이름 등 일관된 보조 기준으로 정렬한다.

닉네임·티어·RP와 실험체 5개 행을 중심으로 화면을 구성한다. 수집 범위, 마지막 갱신 시각은 하단에 짧게 표시한다. 모바일 줄바꿈을 고려해 긴 장비·특성 목록을 시즌 화면에 넣지 않는다. 다른 유저와의 비교 버튼은 추가하지 않는다.

### 10.2. 시즌 정보와 평균 피해량의 출처

- 시즌 자료: 공통 `Season` 자료에서 현재 활성 시즌을 식별한다. 플레이어의 마지막 경기 시즌이 현재 시즌이라고 가정하지 않는다.
- 현재 RP·순위: 랭크 API의 최신 응답 또는 갱신 시각이 표시된 캐시를 사용한다.
- 티어 이름: 랭크 API의 문서상 주요 필드는 RP와 순위다. 티어 문자열이 직접 반환된다고 가정하지 않는다. 구현 시 해당 시즌의 공식 티어 기준 및 상위 티어의 순위 조건을 확인해 변환해야 한다. 기준을 확인하지 못하면 RP·순위만 표시하고 임의 티어를 붙이지 않는다.
- 시즌 TOP 5: 사용자 통계 API의 실험체별 플레이 횟수를 사용한다. 이 자료가 실패하면 DB에 수집된 경기의 TOP 5를 보여줄 수 있지만 반드시 ‘수집된 경기 기준’으로 표시한다.
- 실험체별 평균 피해량: DB의 해당 시즌·랭크·실험체 기록에서 `damageToPlayer`를 집계한다. 사용자 통계 API의 문서에 실험체 평균 피해량은 명시되지 않아 직접 제공된다고 가정하지 않는다.

사용자 통계와 랭크의 엔드포인트·응답 정의는 [공식 레퍼런스](https://developer.eternalreturn.io/static/media/OpenAPI_KR_20260724.html)를 기준으로 한다. 시즌 통계·티어 변환은 이 보고서 보완 단계에서 실측 구현하지 않았다.

**시즌 80경기 / 피해량 표본 35경기**처럼 전체 플레이 횟수와 평균의 분모를 구분해야 한다. DB가 불완전하면 평균 피해량에 ‘수집된 경기 기준’을 붙인다. 최근 90일 밖의 미수집 경기는 지금부터 API를 호출한다고 복구된다고 보장할 수 없다. 표본이 없으면 0이 아닌 ‘데이터 없음’으로 표시한다.

### 10.3. 추가 호출 예산

공통 자료와 UID가 준비됐고 캐시를 새로 갱신하는 정상 요청 기준:

| 요청 | API 비용 |
|---|---:|
| 시즌 TOP 5 통계 갱신 | `/v2/user/stats/uid/{uid}/{seasonId}/3` 1회 |
| 현재 RP·순위 갱신 | `/v1/rank/uid/{uid}/{seasonId}/3` 1회 |
| 실험체별 평균 피해량 계산 | 저장 기록만 사용하면 0회 |
| 위 두 프로필 API 모두 갱신 | 합계 2회 |
| 최신 경기 페이지도 함께 갱신 | 통상 합계 3회, 추가 경기 페이지는 별도 |

UID를 새로 찾으면 1회, 공통 시즌 자료를 갱신하면 공유 비용 1회가 추가된다. 유효한 프로필 캐시를 재사용하면 해당 호출은 생략할 수 있다. 통계 응답에도 RP·순위가 있으므로 요구 필드가 실제 응답에서 충족되면 랭크 호출을 생략하는 최적화는 가능하지만, 최초 구현의 확정 비용으로 약속하지 않는다.

`/전적` 상단 티어는 이 프로필 캐시를 공유한다. 최신 경기는 바로 갱신하되 티어까지 매번 새로 조회할지는 별도 정책으로 정한다. 항상 최신 티어까지 보장하려면 기존 경기 조회 예산에 랭크 요청 1회를 더해야 한다.

루트 제목·구성 조회는 이번 범위에서 제외했으므로 기본·상세·시즌 명령 모두 루트 API 비용 0회다.

## 11. 평균 피해량 표시의 최종 결정

전체 유저·등록 친구·외부 표본과의 평균 비교 기능은 제외한다. 이를 위한 전체 참가자 수집, 외부 통계 연동, 비교 평균 테이블도 만들지 않는다. 공개 API에서 전체 유저의 실험체별 평균 피해량을 직접 제공하는 엔드포인트는 확인되지 않았으며, 자체 표본을 구축하는 방향도 이번에는 진행하지 않는다.

`/시즌전적`의 평균 피해량은 **검색한 유저가 해당 실험체로 플레이한 현재 시즌 랭크 기록**만 대상으로 한다.

- 계산: 해당 조건에서 유효한 `damageToPlayer` 합계 / 유효 경기 수.
- 결측치는 0으로 대체하지 않는다. 유효한 0 피해량은 실제 값으로 포함한다.
- 시즌 전체 플레이 횟수와 피해량 계산에 사용한 표본 수를 구분한다.
- 일부 경기만 수집했으면 ‘수집된 경기 기준’으로 표시하고, 표본이 없으면 ‘데이터 없음’으로 표시한다.
- 다른 유저 평균 대비 백분율, 잘함·못함 등급, 외부 기준 비교 버튼은 표시하지 않는다.
- `/전적분석`의 **본인 과거 ↔ 본인 최근** 비교는 원래 요구사항대로 유지한다.

예시 행(가상 수치): **리오 · 시즌 80경기 · 평균 피해 25,430 · 피해량 표본 35경기**.

### 이번에 구현하지 않을 기능

### 추천 착수 순서

0. **개발·운영 분리**: 운영에서 이터널 리턴 명령·API·수집이 활성화되지 않도록 기능 설정과 명령 등록·시작 경로를 분리한다.
1. **공통 API 대기열**: 초당 1회 준수, 수동 요청 우선, 재시도·중복 작업 통합.
2. **DB와 응답 모델**: 경기·유저·수집 상태·공통 자료·시즌 프로필 저장.

4. **자동 갱신**: 지정 유저 관리와 5분 주기, 엔드필드와 독립 실행.
5. **시즌 프로필과 집계**: 현재 시즌·티어 기준 검증, TOP 5, 자기 평균, 본인 과거·최근 계산.
6. **디스코드 화면**: 기본 전적 → 상세 전적 → 시즌전적 → 전적분석 순으로 연결.
7. **통합 검증과 운영 반영**: 호출 간격·페이지 누락·모바일 가독성·기존 기능 회귀 확인.

초기 과거 수집 100경기, 목록 페이지당 5경기, 분석 최근 50경기와 그 이전 50경기는 구현 시작용 기본값 제안이다. 일반·랭크 혼합 수집에서 특정 모드 100경기가 확보된다고 가정하지 않는다. 모드·실험체별 표본 부족과 시즌 기록 공백을 화면에 표시한다. 추가 수집은 목표 범위까지 이어가되 API가 제공하지 않는 과거까지 확보했다고 표시하지 않는다.

상세 작업과 완료 기준은 [구현 TODO](eternal-return-implementation-todo.md)에 정리했다. 0~3단계는 코드·검증까지 완료했으며 다음 작업은 4단계 지정 유저 관리와 5분 자동 갱신이다.

## 13. 개발 중인 이터널 리턴 기능의 운영 노출 방지

### 변경 전 구조의 문제

변경 전 `src/commands/index.ts`는 이터널 리턴 명령을 공통 목록에 항상 포함했다. `src/register-commands.ts`도 이 목록을 그대로 등록했다. API 키를 비워도 명령은 나타났고 공통 미지원 명령 안내에도 전적 명령 이름이 들어 있었다.

### 권장 분리 방식

같은 저장소를 유지하면서 환경별 기능 활성화와 배포 대상을 분리한다. `ER_ENABLED`와 설정에 따른 명령 등록·실행 분리는 구현했으며, 실제 운영 환경 적용은 별도다.

| 구분 | 개발용 봇 | 미니PC 운영 봇 |
|---|---|---|
| `ER_ENABLED` | `true` | `false` 또는 미설정 |
| 이터널 리턴 명령 | 개발 앱/서버에 등록 | 등록 대상에서 제외 |
| 전적 API·모니터·전용 DB 초기화 | 활성화 | 시작하지 않음 |
| KIS·엔드필드 | 각 환경의 기존 설정대로 | 기존 기능 계속 운영 |
| Discord 인증·DB | 개발용 앱·토큰·DB | 운영용 앱·토큰·DB |
| 배포 코드 | 기능 개발 작업 브랜치 | 검증한 운영 커밋/릴리스 |

설정을 명령 등록과 실행 처리에 함께 적용한다. 미니PC에서 키를 제거하는 것만으로 명령을 숨길 수는 없다. 이전에 등록된 이터널 리턴 명령은 관리 중인 운영 애플리케이션의 등록 범위를 확인해 정리해야 한다. 전역 명령과 서버 명령은 별도 범위이며 한쪽만 갱신해 다른 범위의 명령까지 삭제됐다고 가정하지 않는다. [Discord 공식 명령 문서](https://docs.discord.com/developers/interactions/application-commands)

개발용·운영용 봇이 서로 다른 Discord 애플리케이션인지 구현 시 확인한다. 동일 앱 토큰을 두 환경에서 사용하면 등록한 명령 목록이 같은 앱에 반영되므로 토큰·앱까지 구분하는 것이 적합하다. 현재 미니PC의 실제 인증 설정은 확인하지 않았다.

이터널 리턴 내부 코드는 기능 모듈로 묶고 활성 상태에서만 로드·시작한다. 단순 폴더 이동만으로 등록·실행이 차단되지는 않는다. 기능 스위치를 꺼도 소스가 배포물에 존재할 수 있으며 공통 코드의 빌드 오류까지 방지하는 것은 아니다. 미완성 코드 자체도 운영에 포함하지 않으려면 전적 개발 작업 브랜치를 유지하고, 주식·공지 수정만 검증된 운영 커밋으로 배포한다.

### 0단계 구현 결과 — 2026-09-16

- `ER_ENABLED`가 false/미설정이면 키 전달·전적 모듈 로드·명령 실행을 차단한다. true인 로컬 개발 환경에서만 켠다.
- 전역·서버별 이전 전적 명령을 골라 정리하는 등록 도구와 미리보기 기능을 추가했다. 실제 Discord 등록 변경은 실행하지 않았다.
- `.env.example`은 false로, 로컬 개발 `.env`는 true로 설정했다. 미니PC 설정과 운영 DB는 변경하지 않았다.
- `codex/er-environment-isolation` 브랜치에서 기존 미커밋 작업을 보존하며 구현했다. 커밋·푸시는 하지 않았다.
- 타입 검사, 전체 테스트 160개, 빌드 통과. 비활성 진단 도구의 API 호출 전 종료도 확인했다.
- 전적 자동 수집·전용 DB는 다음 단계에서 구현한다. 현재의 비활성 경계 밖에서 해당 서비스를 초기화하지 않는 원칙을 유지한다.
- 개발·운영의 실제 앱/토큰 분리 확인, 미니PC 명령 정리·재시작은 운영 적용 단계에 남아 있다. 절차는 README의 개발·운영 분리에 정리했다.

## 14. 4·5단계 구현 결과 — 2026-09-16

### 자동 갱신과 관리

- `npm run manage:eternal-return -- add|list|disable` 로 자동 수집 대상을 명시적으로 관리한다. `/전적` 검색만으로는 자동 등록되지 않는다.
- 이터널 리턴 모니터는 엔드필드 공지 및 Discord 알림 채널과 독립적으로 실행한다. 봇 시작 직후 한 번 확인하고 `ER_REFRESH_INTERVAL_MS`(기본 300,000ms)마다 다음 확인을 예약한다.
- 한 주기가 끝난 뒤 다음 주기를 예약하며, 수동 검색과 자동 갱신이 같은 UID에서 겹치면 수집 Promise를 공유한다. 한 유저의 실패는 다음 유저를 막지 않는다.
- 기존 경기만 다시 받은 경우 `storedGames=0`으로 계산하고 마지막 성공 확인 시각만 갱신한다. 자동 갱신은 Discord 메시지를 보내지 않고 요약 로그만 남긴다.

### 시즌 프로필과 분석

- 현재 시즌은 공식 `Season` 자료에서 `isCurrent=1`인 행으로 결정한다. 확인 당시 API 시즌 ID는 41, 내부 이름은 `Season21`이었다.
- 프로필 갱신은 `/v2/user/stats/uid/{uid}/{seasonId}/3`와 `/v1/rank/uid/{uid}/{seasonId}/3`을 각 1회 사용하고 5분간 SQLite에 캐시한다.
- `홉빵맨` 실측에서 시즌 41 통계는 `userStats` 배열 1건으로 반환됐고 MMR 4,648, 시즌 28경기, `characterStats` 3건이었다. 모델과 테스트는 공식 배열 응답을 기준으로 한다.
- 현재 시즌 ID 41의 티어 경계를 공식 랭크 안내 기준으로 버전 고정했다. 다른 시즌에는 확인되지 않은 티어 이름을 계산하지 않는다.
- 선호 실험체는 사용자 통계의 시즌 플레이 횟수를 우선한다. 응답이 5개보다 적으면 같은 시즌·랭크의 수집 경기 횟수로 보완한다.
- 평균 피해량은 DB에 저장된 검색 유저 본인의 `damageToPlayer`만 사용한다. 결측치는 제외하고 실제 0은 포함하며, 시즌 경기 수·수집 경기 수·피해량 표본 수를 따로 반환한다.
- 분석 기본값은 같은 모드의 최근 50경기와 직전 50경기다. 평균 피해량·순위·킬·데스·어시스트·팀킬을 전체 및 실험체별로 계산하며 항목별 유효 표본 수와 패치 목록을 함께 반환한다.
- 외부 유저 평균, 백분율, 잘함·못함 판정은 구현하지 않았다.

Discord의 `/시즌전적`과 `/전적분석` 화면 연결은 6단계 범위다. 4·5단계는 데이터 수집, 캐시, 계산 및 운영 수명주기까지 완료했다.
